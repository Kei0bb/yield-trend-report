# Yield Portal — 今後の拡張計画 (Roadmap)

このドキュメントは、現状（社内 LAN・少人数・閲覧専用）から将来の拡張を見据えた
**やるべきことの整理**です。各項目には「なぜ必要か」「いつ必要になるか（トリガー）」
「概算の規模感」を添えています。優先度は固定ではなく、利用状況に応じて見直します。

運用・インフラ面の手順詳細は [`deploy-windows.md` セクション 12](./deploy-windows.md) に
既に記載があります。本書はそれを含めた**全体像**として、機能・データ層・
アーキテクチャまでをまとめます。

---

## 現状サマリ（2026-06 時点）

| 項目 | 現状 |
|---|---|
| アクセス | 共有 Windows マシン上で `http://yieldportal.socionext.com`（nginx → uvicorn :8000）を計画中。平文 HTTP。 |
| 認証 | なし（社内 LAN・閲覧専用のため不要） |
| ページ | Dashboard（一覧）/ Report（単一製品トレンド + PDF）/ Explore（ロット drill-down） |
| データ | Oracle `SEMI_CP_HEADER` / `SEMI_CP_BIN_SUM`。CP/FT/SLT を `PROCESS` 列で区別。 |
| キャッシュ | メモリ内 3h TTL（単一プロセス） |
| 設定 | `product_config.yaml`（製品ごとの process / report ユニット / bin_group） |
| デプロイ | 手動（git pull → build → サービス再起動） |

---

## フェーズ分け

- **短期 (今〜数ヶ月)** — 利用が増える前に入れておくと後が楽になる、低コストな整備
- **中期 (利用拡大・他チーム展開時)** — 人が増える／製品が増えると顕在化する課題
- **長期 (本格運用・全社展開時)** — 規模・信頼性・自動化が要求される段階

各項目の `[トリガー]` が、その作業を実際に始める判断基準です。**トリガーが来る前に
先回りして実装しないこと**（特にインフラ系は過剰投資になりやすい）。

## A. インフラ / 運用

> 手順の詳細は [`deploy-windows.md` セクション 12](./deploy-windows.md) を参照。

### A-1. HTTPS 化 〔中期〕
- **なぜ:** 認証（ログイン）を入れる前提条件。平文だとパスワードが盗聴され得る。
- **トリガー:** 認証を入れる直前 / 社内ポリシーで HTTP が許容されなくなったとき。
- **規模感:** 小。`deploy/nginx.conf` の HTTPS `server` ブロックのコメントを
  外すだけ。社内発行の証明書を IT 部門から入手して配置。アプリ本体は無変更。

### A-2. 認証 / アクセス制御 〔中期〕
- **なぜ:** 閲覧者が増える・他チームに展開する際、誰がアクセスできるかの管理が要る。
- **トリガー:** チーム外への公開 / 製品単位の閲覧制限が必要になったとき。
- **規模感:** 段階的。まず nginx `auth_basic`（共有 PW 1 つ）→ 必要に応じて社内 SSO
  (SAML/OIDC)。SSO はアプリ側にも変更が入るため中規模。

### A-3. シークレット管理 〔短期〜中期〕
- **なぜ:** Oracle パスワードが平文 `backend/.env` にある。共有マシン上のリスク。
- **トリガー:** マシンへのアクセス者が増える / 監査要件が出たとき。
- **規模感:** 小〜中。Windows 資格情報マネージャ or シークレットストアへ移行。

### A-4. 監視 / バックアップ / ログ管理 〔中期〕
- **なぜ:** サービス停止に気づけない・ログが無限に溜まる。
- **トリガー:** 「落ちていて気づかなかった」が一度でも起きたとき。
- **規模感:** 小。`/health` への死活監視、ログローテーション（nginx は自動
  ローテーションしないため手動/タスクスケジューラ対応が必要 — deploy-windows.md
  参照）、uvicorn ログのローテーション、復旧手順の文書化。

### A-5. デプロイ自動化 〔長期〕
- **なぜ:** 現状は手動 git pull → build → 再起動。手順ミス・属人化のリスク。
- **トリガー:** 更新頻度が上がる / 複数人がデプロイするようになったとき。
- **規模感:** 中。更新用 `.bat`／スクリプト化 → CI でのビルド成果物配布。

## B. 機能拡張

### B-1. データエクスポート (CSV / Excel) 〔短期〕
- **なぜ:** 「画面の数字を Excel に持っていきたい」は現場で必ず出る要望。
  PDF はあるが二次加工できない。
- **トリガー:** 利用者から二次集計の要望が出たとき。
- **規模感:** 小〜中。集計済み DataFrame は既にあるため、`/api/export-csv`
  エンドポイント追加が中心。**PDF 生成ロジック (`pdf_service.py`) には触れない。**

### B-2. 複数製品の同時比較レポート 〔中期〕
- **なぜ:** 現状 Report は単一 `product_id`。類似製品・リビジョン間の比較需要。
- **トリガー:** 「製品 A と B を並べて見たい」要望。
- **規模感:** 中。フロントの選択 UI とバックの複数製品集計。チャート描画の拡張。

### B-3. 異常検知の高度化 〔中期〕
- **なぜ:** 現状 `anomaly_config.yaml` による閾値ベースの警告。トレンド変化や
  工程間の異常相関は拾えない。
- **トリガー:** 閾値だけでは取りこぼす事象が増えたとき。
- **規模感:** 中〜大。移動平均・偏差ベースの検知、bin 構成変化の検知など。

### B-4. レポートの定期自動生成・配信 〔長期〕
- **なぜ:** 「月次レポートを毎月手動で出している」を自動化したい。
- **トリガー:** 定例レポート運用が定着したとき。
- **規模感:** 中。スケジューラ（Windows タスク or アプリ内 cron）で PDF を生成し、
  共有フォルダ配置 or メール配信。**PDF 生成ロジックは現行のまま呼び出す。**

### B-5. 期間・粒度の柔軟化 〔中期〕
- **なぜ:** Report は ISO 週 × 12 固定。日次／月次や任意期間の需要が出うる。
- **トリガー:** 週粒度以外の分析要望。
- **規模感:** 中。集計キー（`lot_id` ロールアップ）の一般化と UI 追加。

## C. データ層

### C-1. FT / SLT の本格活用 〔中期〕
- **なぜ:** スキーマ上は CP/FT/SLT を `PROCESS` 列で扱えるが、運用・設定の
  作り込みは製品ごとにまちまち。
- **トリガー:** FT/SLT を定常的にレポートする製品が増えたとき。
- **規模感:** 中。`product_config.yaml` の整備と、工程横断ビューの検討。

### C-2. 工程間の歩留まり相関・追跡 〔長期〕
- **なぜ:** CP → FT → SLT の歩留まり連動を 1 つの substrate で追えると原因分析が進む。
- **トリガー:** 工程をまたいだ不良解析の需要。
- **規模感:** 大。join キー（SUBSTRATE_ID）を軸にした横断クエリ・データモデル拡張。

### C-3. クエリ性能・接続管理の最適化 〔中期〕
- **なぜ:** データ量・同時アクセスが増えると DB 応答が律速になりうる。
- **トリガー:** 体感で遅くなったとき / 同時利用者が増えたとき。
- **規模感:** 中。接続プールのチューニング、クエリのインデックス確認、
  キャッシュ戦略の見直し（→ D-1 と連動）。

---

## D. アーキテクチャ / 品質

### D-1. キャッシュの共有化・マルチプロセス対応 〔長期〕
- **なぜ:** 現状メモリ内キャッシュは単一プロセス前提。uvicorn を複数ワーカーに
  スケールするとワーカー間でキャッシュが分断される。
- **トリガー:** 単一ワーカーで捌けなくなったとき。
- **規模感:** 中。キャッシュを Redis 等の外部ストアへ移行。

### D-2. テストカバレッジの拡充 〔短期〕
- **なぜ:** 集計ロジック（bin% 分母など）は過去にバグの実績がある。回帰防止が重要。
- **トリガー:** 集計・設定まわりを変更するたび（継続的）。
- **規模感:** 小。既存 `backend/tests/` にケース追加。特に分母・REWORK_NEW・
  substrate 重複まわりの境界値。

### D-3. 設定のバリデーション強化 〔短期〜中期〕
- **なぜ:** `product_config.yaml` は手書き。誤記が実行時まで気づかれにくい。
- **トリガー:** 設定ミスによる不具合が起きたとき。
- **規模感:** 小。起動時 or `/api/debug/config` でのスキーマ検証・警告。

---

## やらないこと / 注意（不変の制約）

- **PDF レポート生成 (`pdf_service.py`) のロジックは変更しない。** 機能追加は
  既存の生成処理を「呼び出す」形で行い、生成ロジック自体には手を入れない。
- 過剰な先回り投資をしない。各項目は `[トリガー]` が来てから着手する。
- lock ファイル（`package-lock.json` / `backend/uv.lock`）はコミット対象のまま
  維持する（再現性のため。gitignore には入れない）。

## 優先度の目安（現時点の推奨順）

1. **D-2 テスト拡充** / **A-3 シークレット管理** — 低コストで効く整備
2. **B-1 CSV/Excel エクスポート** — 要望が出やすく実装も軽い
3. **A-1 HTTPS → A-2 認証** — 利用拡大時にセットで
4. それ以降は利用状況のトリガーに応じて中期・長期項目を判断

> この順序は固定ではありません。実際の要望・運用上の痛みが出た項目を上に
> 繰り上げてください。
